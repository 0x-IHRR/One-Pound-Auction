# One-Pound Auction 模块划分与分支开发顺序

## 1. 目标

当前项目已经完成 MVP demo 闭环，但距离可上线工程化版本仍有明显差距。现阶段不建议继续按页面或前后端零散推进，而应按业务能力分为 4 个主模块推进，保证：

- `main` 始终可运行、可演示、可回归
- 模块边界清晰，减少多人并行时的互相阻塞
- 先做公共底座，再做业务闭环，避免返工

## 2. 模块划分表

| 模块 | 目标范围 | 主要职责 | 不包含 |
| --- | --- | --- | --- |
| `foundation` | 基础工程能力 | 项目结构整理、环境配置、配置管理、日志、统一错误处理、输入校验基础设施、Prisma 迁移规范、CI 基础、通用工具层 | 登录、订单、后台业务功能 |
| `auth-user` | 用户体系 | 登录注册、会话管理、角色模型、用户基础资料、鉴权中间件、页面访问控制 | 商品发布、支付、后台审核 |
| `marketplace-content` | 集市内容域 | 发布、编辑、上下架、列表、详情、搜索/筛选、内容状态流转、内容归属关系 | 支付回调、履约解锁、运营看板 |
| `order-payment-admin` | 交易 + 后台最小闭环 | 订单、支付、支付状态、支付回调、幂等、失败态、退款预留、后台审核/运营基础能力、基础风控与看板 | 完整复杂履约编排、重型运营系统 |

## 3. 分支命名表

建议统一采用 `feat/<module>` 命名，和长期协作、PR 语义、自动化规则更兼容。

| 模块 | 推荐分支名 | 你当前已建分支 | 说明 |
| --- | --- | --- | --- |
| 基线分支 | `main` | `main` | 始终保持可运行 |
| 基础工程 | `feat/foundation` | `foundation` | 当前分支可继续使用；后续如需统一规范，可再重命名 |
| 用户体系 | `feat/auth-user` | `auth-user` | 语义清晰，建议最终统一到 `feat/` 前缀 |
| 内容域 | `feat/marketplace-content` | `marketplace-content` | 与业务模块一致 |
| 交易与后台 | `feat/order-payment-admin` | `order-payment-admin` | 当前收口方式合理，适合 MVP 向工程化过渡 |

## 4. 推荐开发顺序表

| 顺序 | 模块 | 为什么先做 | 关键产出 | 依赖 |
| --- | --- | --- | --- | --- |
| 1 | `foundation` | 这是所有后续模块的公共底座；越晚做，返工越多 | 目录整理、env 规范、日志、错误处理、校验层、Prisma 迁移流程、CI 基础 | 无 |
| 2 | `auth-user` | 内容归属、订单归属、后台权限都依赖用户与角色体系 | 登录/会话、用户表、角色模型、鉴权中间件、基础个人中心 | `foundation` |
| 3 | `marketplace-content` | 有了用户后，内容发布与管理才能形成真实业务主体 | 发布/编辑/上下架、内容状态、列表/搜索/筛选、作者归属、基础内容治理 | `foundation` + `auth-user` |
| 4 | `order-payment-admin` | 交易闭环必须建立在“有用户、有内容、有状态”之上；后台最小能力也应跟交易一起落地 | 订单模型、支付流程、回调与幂等、购买记录、基础审核后台、运营配置 | `foundation` + `auth-user` + `marketplace-content` |

## 5. 各模块建议交付边界

### `foundation`

完成以下内容后，再允许其他模块大规模并行：

- 统一目录与命名约定
- `env` 分层与配置读取入口
- 接口输入校验和错误返回格式
- 数据访问层约束与 Prisma migration 规范
- 基础日志、请求追踪、错误上报预留
- `lint`、`build`、基础 CI 校验跑通

### `auth-user`

必须以最小可用为目标，不要一开始做复杂账户系统：

- 邮箱魔法链接或最简单的第三方登录二选一
- 用户表、会话表、角色字段
- `creator`、`buyer`、`admin` 等最小角色集
- 页面级和接口级鉴权

### `marketplace-content`

这个模块的重点不是“页面多”，而是“状态可控”：

- `AuctionItem` 向正式内容实体演进
- 发布、编辑、草稿、上架、下架、删除等状态
- 作者归属、可见性、审核状态预留
- 列表、详情、筛选能力抽象成统一查询入口

### `order-payment-admin`

当前阶段把交易和后台合并是合理的，能减少等待：

- 订单表、支付表、交易状态机
- 支付前校验、支付后回调、重复回调幂等
- 解锁前置条件沉淀为统一服务
- 后台最小页面：内容审核、订单查看、基础运营配置

## 6. 分支协作规则

- `main` 只接收已经可运行、已自测、可回归的变更
- 所有模块分支都从最新 `main` 切出，并定期同步 `main`
- `foundation` 的公共改动优先合并，避免其余模块长期漂移
- `auth-user` 完成基础鉴权前，`marketplace-content` 和 `order-payment-admin` 只做可兼容的预埋，不做强绑定实现
- 跨模块公共能力优先回收到 `foundation`，不要在业务分支各自复制一套

## 7. 当前阶段的执行建议

如果目标是从 demo 走到可上线版本，建议按下面的节奏推进：

1. 先在 `foundation` 分支解决当前已知 `lint` 问题，并补齐校验、错误处理、配置读取、目录收敛。
2. 再在 `auth-user` 分支落最小用户体系，优先解决“谁发布、谁购买、谁能看”的主体问题。
3. 之后推进 `marketplace-content`，把现有 demo 内容流转改造成正式内容域。
4. 最后在 `order-payment-admin` 中完成订单与后台最小闭环，确保支付、解锁、审核可以串起来。

## 8. 结论

对当前项目体量，`4` 个主模块是合理上限。这个拆法已经兼顾了：

- 足够清晰的业务边界
- 足够低的协作阻塞概率
- 足够强的从 demo 演进到工程化版本的可执行性

如果后续团队人数增加、后台和履约复杂度明显上升，再从 `order-payment-admin` 中拆出 `delivery-fulfillment` 和 `admin-ops` 会更稳。
